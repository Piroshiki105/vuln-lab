攻撃を試す

別のブラウザ(またはプライベートウィンドウ。Cookie は同じホストなら別ポートでも共有されるため)や curl を「攻撃者」として使い、この利用者になりすませるか試してください。

JavaScript から読める Cookie:

攻撃者になりすます

次のコマンドで、この sid を使って別のクライアントからマイページを開けます。

curl -b sid={{.SID}} http://127.0.0.1:8080/session/home
固定化の罠ページを開く
ヒント
  • 推測: /session/login を何度か開くと、セッションIDが連番で発行されるのが分かります。別のアカウントでログインして、前後の番号の Cookie sid を試してください。
  • 固定化: 攻撃者が /session/login でIDを 1 つ受け取り、/session/login?sid=そのID のリンクを被害者に踏ませます。被害者がログインした後、攻撃者が同じ sid で /session/home を開いてください。罠ページは http://127.0.0.1:9090/session/ にあります。
  • 盗用: Cookie に HttpOnly が付いていないため、上の欄のように JavaScript で読めます。XSS(/xss/ の画面)と組み合わせると sid を盗めます。
なぜ危険か / 本来どう直すか

セッションIDは「それを持っている人がその利用者」という合言葉の役目をします。推測できる、外から決められる、盗まれる、のどれかが成り立つと、パスワードを知らなくてもなりすませます。

  • 推測: セッションIDは暗号論的乱数(Go なら crypto/rand)で十分な長さ(128 ビット以上)にする。連番や時刻から作らない。
  • 固定化: ログイン成功時に必ずセッションIDを発行し直し、古いIDは破棄する。URL などで渡されたIDを受け付けない。
  • 盗用: Cookie に HttpOnly(JavaScript から読めなくする)、Secure(HTTPS のみで送る)、SameSite を付ける。サイト全体を HTTPS にする。IDを URL に載せない。
  • ログアウト時にサーバー側のセッションを破棄し、有効期限(アイドル・絶対)を設ける。
本来の対策(コード例)

// 1) ログイン成功時にセッションIDを必ず発行し直す(固定化対策)。
delete(sessions, oldID)
newID := randomID() // 2) crypto/rand で 16 バイト以上の乱数から作る(連番にしない)
sessions[newID] = username

// 3) Cookie に属性を付ける。
http.SetCookie(w, &http.Cookie{
    Name: "sid", Value: newID, Path: "/",
    HttpOnly: true,                 // JavaScript から読めない
    Secure:   true,                 // HTTPS のときだけ送る
    SameSite: http.SameSiteLaxMode, // 他サイト経由の送信を制限する
})
// 4) URL でセッションIDを受け取らない(?sid= を無視する)。

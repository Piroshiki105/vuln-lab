攻撃を試す

ログインしたまま、別タブで罠ページ http://127.0.0.1:9090/csrf/ を開き、リンクを踏んでからこのページを再読み込みしてください。罠サーバーは別途起動が必要です(cd trap && go run .)。

罠ページを開く
ヒント
  • 罠ページ(別ポート 9090 = 別オリジン)のフォームが、このサイトの /csrf/transfer や /csrf/password に POST しています。
  • ブラウザは送信先のサイトの Cookie を自動で付けます。リクエストを出したのがどのサイトかは関係ありません。
  • 送金後に残高、パスワード変更後に再ログインで確認してみましょう。
なぜ危険か / 本来どう直すか

サーバーが「Cookie が正しい = 本人が意図して操作した」と見なすと、攻撃者のページ経由で送られたリクエストも本人の操作として処理されます。被害者はリンクを開くだけで、送金やパスワード変更を実行されてしまいます。

対策は複数あり、組み合わせるのが基本です。

  • CSRFトークン: フォームに推測不能なトークンを埋め込み、サーバーで検証する。
  • SameSite Cookie: SameSite=Lax または Strict を指定する(同一サイト扱いの別ポートからは防げない点に注意)。
  • Origin / Referer 検証: 自サイト以外からの POST を拒否する。
  • 再認証: パスワード変更や送金では、現在のパスワードの再入力を求める。
本来の対策(コード例)

参考用のコードです。この画面では実行されません(この画面は意図的に脆弱なままです)。

// 1) 状態を変える POST には CSRF トークンを付け、サーバーで照合する。
//    フォームを出すときにランダムなトークンをセッションに保存して hidden で埋め込む。
if subtle.ConstantTimeCompare([]byte(r.FormValue("csrf_token")), []byte(session.Token)) != 1 {
    http.Error(w, "不正なリクエストです", http.StatusForbidden)
    return
}
// 2) Origin ヘッダが自サイトか確認する(補助)。
if o := r.Header.Get("Origin"); o != "" && o != "http://"+r.Host {
    http.Error(w, "不正なリクエストです", http.StatusForbidden)
    return
}
// 3) Cookie に SameSite=Lax(または Strict)を付ける。
// 4) パスワード変更などは、現在のパスワードの再入力(再認証)を求める。

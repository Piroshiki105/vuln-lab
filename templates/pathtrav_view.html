ヒント
  • .. は「一つ上のディレクトリ」を表します。自組織のディレクトリ({{.OrgDir}})の外のファイルを指せないでしょうか?
  • 組織IDが連番(1, 2, ...)であることは画面の表示から推測できます。../org2/contract.txt のように、他組織のディレクトリ名を推測して直接指定してみましょう。
  • さらに上の階層へ出れば、docs/ の外、プロジェクト直下の go.mod や secret/ ディレクトリにも届きます。
  • 十分に ../ を重ねれば、OS の /etc/passwd にも届きます。
なぜ危険か / 本来どう直すか

入力されたファイル名をそのままパスに連結すると、../ で公開ディレクトリの外へ出られます。マルチテナントのアプリでは特に深刻で、他のテナント(組織・顧客)のディレクトリに保存された文書や設定ファイルを読み取られる、横断的な情報漏えいにつながります。さらに上の階層まで遡れれば、ソースコード、認証情報、OS のファイルなども対象になります。

対策は次のとおりです。

  • ベースディレクトリ配下か検証: filepath.Join と filepath.Clean で正規化した結果が、許可したディレクトリの配下かを確認する。
  • ルートを固定: Go 1.24 以降は os.Root(os.OpenRoot)で、ルート外へのアクセスを封じられる。http.FileServer + http.Dir も利用できる。
  • 許可リスト: ファイル名を ID にマッピングし、利用者に生のパスを指定させない。
  • テナント分離の二重化: パスの検証に加え、アプリ側でも「このファイルが自分のテナントの所有物か」をDB等で確認する。ディレクトリ名を組織IDから単純に作らず、推測しにくい識別子にする。
  • 権限の最小化: アプリの実行ユーザーが読める範囲を絞る。

ヒント
  • 件名に改行(\r\n)を入れて、新しいヘッダ行(Bcc: など)を追加できないでしょうか?
  • メールアドレス欄に改行を入れるとどうなるでしょう? 件名やお名前との違いに注目してください(SMTP が宛先として使う値は、ライブラリが検証します)。
  • ブラウザの1行テキスト欄は、キーボードで改行を打とうとしても送信扱いになったり、貼り付けても改行が消えたりします。この画面では件名を複数行の入力欄にしてあり、「入力例を入れる」のボタンで改行入りの例を入れられます。
  • 実際の攻撃では、ブラウザを使わず curl や Burp Suite などでリクエストを直接組み立てます。例: 
    curl -d "name=A&email=victim%40example.com&subject=Hi%0D%0ABcc: attacker%40evil.example&body=Hello" http://127.0.0.1:8080/mail/contact
  • smtp4dev で受信メールを開くと、注入した Bcc: がメールの「Headers」に現れます。ただし、実際の配送先は SMTP の RCPT TO(入力したメールアドレス)で決まるため、Bcc: ヘッダを足しただけでは Bcc 先には届きません。sendmail -t のようにヘッダから宛先を拾う実装では、実際に配送されて被害になります。
  • 配送先は変わらなくても、被害者に届くメールの中身は書き換えられます。
    • 偽の文言の差し込み: 件名に \r\n\r\n を入れるとヘッダが終わり、続きが本文になります。サポート窓口から届いたメールの先頭に、攻撃者の文言が入ります。
    • HTMLメールへの差し替え: Content-Type: text/html を注入すると本文が HTML として扱われ、偽の見出しやリンク(フィッシング)を差し込めます。末尾の <!-- で、元の本文は HTML コメントの中に隠れます。
    • Reply-To の注入: Reply-To: を足すと、被害者が「返信」したときの宛先を攻撃者のアドレスにできます。
なぜ危険か / 本来どう直すか

SMTP(メール送信プロトコル)は、メールヘッダを \r\n で区切られた行の並びとして解釈します。入力値をそのままヘッダに連結すると、入力に含まれる改行がヘッダの区切りとして解釈され、攻撃者は任意のヘッダ(Bcc での不正な宛先追加、Reply-To の偽装など)や本文を注入できます。このフォームのように「入力されたアドレスへ自動返信する」機能では、攻撃者が他人のアドレスを指定することで、正規の窓口の名前で届くフィッシングメール・スパムの送信元として悪用されます。

対策は次のとおりです。

  • 入力に改行を含めない: 件名・お名前・メールアドレスなど、1行であるべき値に \r や \n が含まれていないか検証し、含まれていれば拒否する。
  • 専用ライブラリを使う: Go では net/mail の Address 型や mime.QEncoding のような、ヘッダを安全に組み立てる仕組みを使い、文字列連結を避ける(QEncoding は改行をエンコードするため、ヘッダの区切りとして解釈されなくなる)。
  • アドレスの構文検証: net/mail.ParseAddress で検証する(改行を含む値はここで弾かれるべき)。
  • 自動返信の悪用を抑える: 同一の宛先・送信元への送信回数を制限する。確認済みのアドレスにのみ送る。

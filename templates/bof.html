バッファオーバーフロー(解説のみ)

IPA「安全なウェブサイトの作り方」1.10 に対応する解説ページです。このアプリは Go で書かれており、Go は通常の書き方ではバッファオーバーフローを起こさないため、再現する画面はありません。どんな時にどんな攻撃がされうるかを、ここで説明します。

バッファオーバーフローとは

プログラムは、入力を受け取るために、メモリ上に決まった大きさの領域(バッファ)を確保します。入力の長さを確認せずに書き込むと、確保した領域を超えて隣のメモリを上書きしてしまいます。これがバッファオーバーフローです。

/* 例: C で書かれた CGI。名前を 16 バイトの領域にコピーしている */
char name[16];
strcpy(name, getenv("QUERY_STRING"));   /* 長さを確認しないので、17 バイト以上で溢れる */

溢れた部分に、関数の戻り先アドレスなど、プログラムの動きを決める値が置かれていると、攻撃者が書き込んだ値で動きを乗っ取れます。

どんな時に起きるか

  • C / C++ / アセンブラなど、メモリを直接扱える言語で書かれた部分がある時。独自の CGI、サーバーに組み込むモジュール、他の言語から呼び出すネイティブの拡張などが該当します。
  • 入力の長さを確認せずにコピーする時。strcpy、sprintf、gets や、長さを自分で計算して間違えた memcpy などです。
  • PHP、Perl、Java などのライブラリの中に、C で書かれた部分がある時。アプリ自体が安全な言語でも、画像・文字コード変換・圧縮・暗号などのライブラリが C で書かれていることがあります。
  • 古いバージョンのライブラリや製品を、更新せずに使っている時。IPA は、ウェブサイトそのものでの届出はないものの、ソフトウェア製品では継続して届出を受けていると述べています。

どんな攻撃がされうるか

攻撃やり方起きること
サービス停止(DoS) 長すぎる値や、想定外の値を含むリクエストを送り、プログラムを異常終了させる ウェブアプリケーションやサーバーが落ち、意図しないサービス停止になる
任意のコード実行 溢れさせた領域に、実行させたいコードと、そこへ飛ばすための値を書き込んだリクエストを送る サーバー上で攻撃者のコードが動く。ウイルス・ボットへの感染、バックドアの設置、他のシステムへの攻撃、重要情報の漏えいにつながる
メモリの内容の漏えい 領域の外側を「読み出す」ように仕向ける(バッファオーバーリード) 同じプロセスのメモリにある、鍵・パスワード・他の利用者のデータが漏れる。2014 年の OpenSSL の脆弱性(Heartbleed)が有名

攻撃者は、HTTP のリクエストを送るだけで、これらを試せます。リクエストの種類(パラメータ・ヘッダ・ファイルアップロード)を問いません。

Go ではどうか

  • Go は配列やスライスの範囲を実行時に確認します。範囲外へのアクセスは、メモリを壊さずに panic になります(net/http は、1 つのリクエストの panic を捕まえて、サーバー全体は落としません)。そのため、通常の書き方では、メモリを書き換えて任意のコードを実行させる攻撃にはなりません。
  • ただし、次の部分では、範囲の確認が働かず、バッファオーバーフローが起こりえます。
    • unsafe パッケージでポインタを直接操作する部分
    • cgo で呼び出す C のライブラリ・自作の C コード
    • Go から呼び出す、C / C++ で書かれた外部コマンドやライブラリ
本来どう防ぐか(IPA の対策)
  • 10-(i)-a(根本的解決): ウェブアプリケーションを、直接メモリにアクセスできない言語(Go、Java、PHP、Perl など)で書く。
  • 10-(i)-b: C / C++ などで書く部分を最小限にし、その部分に脆弱性がないかを集中的に確認する。長さを指定できる関数(strncpy ではなく、境界を確認する安全な書き方)を使い、入力の長さを必ず確認する。
  • 10-(ii): 使用しているライブラリや製品を、脆弱性が修正されたバージョンに更新する。
  • 共通の対策として、OS やコンパイラの保護機能(スタックの保護、ASLR など)を有効にする。ただし、これだけで脆弱性が消えるわけではありません。

対応する CWE: CWE-119(メモリバッファの範囲内での操作の不適切な制限)

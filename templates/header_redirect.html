HTTPヘッダインジェクション: リダイレクト

ログイン後などに「元のページへ戻る」ためのリダイレクト先を指定できる画面です。 Go の net/http は本来この種の注入を防ぎますが、この画面は http.Hijacker で 生のTCP接続を乗っ取ってレスポンスを自分で組み立てており、その保護が働きません。

この欄に %0D%0A という文字をそのまま入力しても、ブラウザが % を さらにエンコードしてしまうため届きません。URLバーに直接貼り付けるか、下のボタンを使ってください。

ワンクリックで試す

Set-Cookieを注入する ページ内容ごと差し替える
ヒント
  • 「Set-Cookieを注入する」のリンク先は next=/%0D%0ASet-Cookie: admin=true(URLデコードすると改行)です。レスポンスヘッダに注目してください(curl -i や devtools の Network タブ)。
  • curl -i "http://127.0.0.1:8080/header/redirect?next=%2F%0D%0ASet-Cookie%3A%20admin%3Dtrue" を実行すると、サーバーが返した生のレスポンスをそのまま確認できます。
  • 改行をもう一つ重ねて空行(ヘッダの終端)まで注入すると、その後ろに書いた内容が丸ごとレスポンスの本文として扱われます。「ページ内容ごと差し替える」ボタンで確認してください。
  • 末尾に Connection: close のような文字列がそのまま表示されることがあります。これは、注入によってヘッダが早く終わってしまった後、サーバー側の後続処理がそのまま本文として出力されてしまうためです。実際の攻撃でもよく見られる現象です。
なぜ危険か / 本来どう直すか

HTTPはヘッダとボディを \r\n(CRLF)で区切って解釈します。ヘッダの値に利用者の入力をそのまま連結すると、入力に含まれる改行がヘッダの区切りとして解釈され、任意のヘッダの追加(Set-Cookie によるセッション固定化、キャッシュ制御ヘッダの偽装など)や、ヘッダを早期に終端させてのレスポンス本文の注入(反射型XSS、ページの改ざん)につながります。プロキシやキャッシュサーバーを経由する構成では、1つのTCP接続に偽のレスポンスをまるごと紛れ込ませ、別の利用者への応答をすり替える「レスポンス分割」として、より深刻な被害(キャッシュ汚染)に発展することもあります。

対策は次のとおりです。

  • 標準のAPIをそのまま使う: Go の net/http は w.Header().Set や http.Redirect を使う限り、ヘッダ値の改行を検証して防いでくれる。今回のように http.Hijacker で生のレスポンスを自作しない。
  • 入力に改行を含めない: リダイレクト先などヘッダに使う値は、改行を含んでいないか検証する。
  • リダイレクト先の許可リスト化: 自サイト内の固定パス、または許可したドメインのみを受け付ける(オープンリダイレクト対策にもなる)。
